# Near-miss: v0.9.3 publish mishaps (2026-10-12)

Two command mistakes occurred while publishing v0.9.3 (the release-operations
session that merged PR #41 and republished the release). No user data was
touched and both were corrected within minutes, but the potential severity was
high. Written up at the operator's request, including an analysis of what in
the session trace may have led to them.

## What happened

### 1. Fabricated full SHA for the release target

`gh release create v0.9.3 --target <sha>` was called with a 40-character
string whose prefix matched the abbreviated SHA visible in `git log` output
(`1623bd1`) and whose remaining characters were invented. GitHub rejected it
(`Release.target_commitish is invalid`), leaving the repository without a
v0.9.3 release for a short window — during which `releases/latest` (the
endpoint installed clients query) served v0.9.2.

**Why:** the session memory contained the exact hazard note —
"`gh release create --target` rejects short SHAs; pass the full SHA" — but
instead of *deriving* the full SHA with `git rev-parse HEAD` (one command),
the agent completed the string from the short form it could see on screen.
Knowledge of the rule existed; the rule was not executed.

### 2. Recursive delete aimed at the whole temp root

Cleanup after the failed create ran
`rm -r "$TEMP" -f "$TEMP/v093-repub"` — the entire user temp directory was
passed as a delete target alongside the intended wheel directory, with a
duplicated, misplaced `-f`. It deleted the just-built wheel and churned
through other applications' temp files (Docker Desktop update payloads; many
were locked and survived). Nothing project- or user-data-related lived in
TEMP, but a shared machine's temp root is never a safe delete target.

**Why:** the intent was "clean up this task's artifacts", but the command
enumerated a parent root rather than the specific paths the task had created.
The malformed flag placement indicates hurried construction.

## Impact

Contained: both artifacts (release, wheel) were rebuildable; the release was
recreated within minutes; no user data or project state was lost. Potential
severity was higher — a shared-machine temp root can hold in-use files from
running applications, and a wrong release target could have tagged the wrong
commit had the string happened to be valid.

## Contributing factors (from the session trace)

1. **Session length (~400K tokens of context at the time).** Both errors
   happened deep into a single session that had already published an RC, a
   final release, diagnosed a production detection failure, fixed two install
   scripts, and reinstalled production twice. Late-session commands showed
   measurable sloppiness: a reconstructed identifier instead of a derived
   one, and a cleanup command with duplicated flags and an over-broad target.
   The common shape: *remembering earlier outputs substituted for verifying
   current state with tools.*
2. **Hazard knowledge stored away from the command site.** The full-SHA
   gotcha was known and even written down (project memory), but nothing at
   the point of execution forced the derivation step.
3. **Cleanup-by-intent instead of cleanup-by-enumeration.** "Remove what
   this task created" invites over-broad targets. The safe form names exactly
   the paths the task created.
4. **Success momentum.** A long preceding run of successful state-changing
   operations (two releases, prod reinstalls, shortcut surgery) normalizes
   risk right before the mistakes.

## Mitigations

- Full SHAs only via `git rev-parse` at the moment of use — never typed,
  never extended from a short form. (Better: wrap the release publish in a
  script that takes a tag and resolves the SHA itself.)
- Destructive commands enumerate exactly the paths created in the task;
  never a parent or root (`$TEMP`, `/tmp`, `$HOME`). `ls` the target
  immediately before `rm -r`.
- During multi-step publishes, "delete" to a scratch/move step at the end.
- Long-session rule: before any irreversible command, re-derive every mutable
  input (SHAs, paths, versions) with read-only tools, regardless of what an
  earlier output showed.
- Keep release gotchas adjacent to the execution path (a release script),
  not only in memory notes.
